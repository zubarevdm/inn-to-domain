# Задание 2. Пайплайн «ИНН → домен»

Код: https://github.com/zubarevdm/inn-to-domain

```
$ inn2domain 7721581040
{"domain": "dadata.ru"}

$ inn2domain 7805590027
{"domain": null}
```

Второй пример важнее первого. ООО «ПЛАСТ» из Петербурга сайта не имеет, при этом
домен plast.ru существует и принадлежит другой компании из Москвы. Пайплайн
отвечает null. Вся его конструкция подчинена одной идее: неверный домен в
справочнике дороже пустого поля, потому что пустое поле клиент увидит, а
неверное примет за правду.

## Инструменты

Стек российский, работает без VPN и зарубежных карт: **GigaChat** для анализа,
**Yandex Search API** для поиска (русский малый бизнес Яндекс индексирует полнее
зарубежных поисковиков), **DaData** для карточки организации по ИНН. Поисковый
провайдер меняется одной переменной окружения, второй реализацией подключён Exa.

Python, httpx, pydantic. Фреймворки вроде LangChain я сознательно не брал: в
задаче четыре шага и одна модель, а прозрачность решений важнее готовых
абстракций. Ответы поиска, страницы и вызовы LLM кэшируются в SQLite: бесплатные
лимиты конечны, а прогоны оценки качества должны воспроизводиться.

## Этапы

**1. Валидация ИНН по контрольной сумме.** Мусор не доходит до платных API.

**2. Карточка организации из ЕГРЮЛ через DaData.** Нужна по двум причинам. По
одному ИНН поисковик выдаёт агрегаторы реквизитов, самого сайта в выдаче нет,
поэтому искать надо по названию, бренду и городу. А проверять найденное надо по
ИНН и ОГРН. Карточка даёт и то, и другое, плюс статус организации.

**3. Пять поисковых запросов.** Каждый слеп по-своему. Запрос по ИНН выводит
агрегаторы, зато их сниппеты часто содержат адрес сайта. Запрос по названию
юрлица бесполезен, когда бренд с ним не совпадает: ООО «Интернет Решения» это
ozon.ru, ООО «Дейта Кью» это dadata.ru. Запрос по названию с городом помогает
малому бизнесу с типовым именем.

**4. Сборка кандидатов.** Домены нормализуются: www убирается, punycode
раскрывается в юникод, поддомены схлопываются до значимого имени. Для
конструкторов сайтов сделано исключение: `my-shop.tilda.ws` остаётся целиком,
там поддомен и есть сайт компании.

Агрегаторы и маркетплейсы обычный блок-лист выбрасывает целиком, и это ошибка:
каждый такой портал сам является чьим-то сайтом. По ИНН 7704217370 правильный
ответ это ozon.ru. Правило поэтому мягче: портал проходит дальше, если на его
главной или в контактах опубликованы реквизиты запрошенной организации, либо
домен совпадает с её брендом. Чужие ИНН площадки публикуют на глубоких
страницах, куда пайплайн не заходит, так что ложных срабатываний это не
добавляет.

Второй источник кандидатов это домены, написанные словами в тексте выдачи
(«Сайт: ozon.ru» в карточке агрегатора). Вернуть агрегатор как ответ нельзя,
а взять его подсказку и проверить самостоятельно можно.

**5. Проверка кандидатов.** Главный этап и основной источник уверенности. Для
каждого кандидата загружаются главная страница, найденные в разметке ссылки на
контакты и реквизиты, а также типовые адреса `/contacts`, `/about`, `/rekvizity`,
`/privacy` напрямую: у одностраничников и сайтов на JavaScript ссылок в HTML нет.
В тексте ищется ИНН и ОГРН организации, цифры могут быть разделены пробелами.

Две ловушки ломают наивный поиск подстроки. Первая: в подвале стоит ИНН
веб-студии, «разработка сайта, ООО ...». Вокруг найденного номера проверяется
контекст, такое совпадение помечается и вес теряет. Вторая: бухгалтерские фирмы
и агрегаторы публикуют чужие реквизиты пачками, отсюда правило для порталов.

Дополнительно опрашивается WHOIS. Реестр .ru отдаёт поля `org` и `taxpayer-id`,
то есть название и ИНН владельца домена, и это была бы прямая официальная
связка. Проверка на живых доменах показала, что сейчас оба поля скрыты:
у yandex.ru, gazprom.ru, rzd.ru, wildberries.ru и у мелких доменов они приходят
пустыми. Остаётся дата регистрации, нужная для контроля перехвата
освободившихся доменов. Код к появлению этих данных готов.

**6. Решение LLM.** GigaChat получает карточку организации и кандидатов со всеми
собранными доказательствами, возвращает строгий JSON с доменом, уверенностью и
обоснованием. Два правила снимают известные риски:

- модель выбирает домен из списка кандидатов, ответ вне списка отбрасывается
  кодом. Галлюцинация не может стать результатом;
- содержимое страниц подаётся отдельным блоком с пометкой «недоверенные данные».
  На сайте может лежать текст, адресованный модели.

Если уверенности нет, модель возвращает дополнительный поисковый запрос,
пайплайн выполняет его и спрашивает ещё раз. Не больше двух кругов.

**7. Политика ответа.** Решение принимает код, а не модель:

1. Реквизиты организации найдены на сайте, это ответ с уверенностью 0.9–0.97.
2. Реквизиты нашлись на одном домене, LLM предлагает другой: верю реквизитам,
   уверенность снижаю до 0.75.
3. Реквизитов нет, LLM уверена не ниже 0.6: требуется независимый признак.
   Адрес сайта из карточки организации, домен корпоративной почты либо
   совпадение бренда с доменом вместе с городом на странице. Одного совпадения
   названия мало: у ООО «ПЛАСТ» из Петербурга и у сайта plast.ru из Москвы
   названия совпадают полностью, а компании разные.
4. Иначе null.

## Оценка качества

Проверял на размеченном наборе из 35 организаций: крупный бизнес, средние
компании, вузы, малые ООО с типовыми названиями и шесть ИП. У 23 из них сайт
есть, у 12 нет. Метки ставились вручную по выдаче и по реквизитам на сайтах,
ответы пайплайна в разметке не участвовали.

Три режима на одном и том же наборе показывают вклад каждого этапа:

| метрика | только поиск | поиск + проверка реквизитов | полный пайплайн |
|---|---|---|---|
| выдано доменов | 34 | 4 | 15 |
| точность | 0.38 | 0.0 | **0.93** |
| полнота | 0.57 | 0.0 | 0.61 |
| верных null | 0.0 | 1.0 | 0.92 |
| неверных доменов | 9 | 4 | **0** |
| ложных ответов там, где сайта нет | 12 | 0 | 1 |

Базовый режим «первый неагрегатор из выдачи» ошибается в двух случаях из трёх и
не умеет молчать: на 12 организациях без сайта он выдал 12 доменов.

Проверка реквизитов без LLM даёт обратную крайность. ИНН на главной или в
контактах публикуют немногие, поэтому режим отвечает 4 раза из 35 и все четыре
раза ошибается. Ошибки поучительные: ИНН «Ростелекома» нашёлся на checko.ru, ИНН
«Альфа-Банка» на alfabank.cards, ИНН вуза на сайте филиала. Отсюда важный вывод,
который я заложил в политику: реквизиты на странице доказывают, что организация
упомянута, но не то, что сайт принадлежит ей. Когда модель называет другой
домен, арбитром выступает она, а её выбор всё равно проходит проверку на опору.

Полный пайплайн отвечает 15 раз и ошибается один раз, причём ни разу не назвал
чужой домен организации, у которой сайт есть. Единственная ошибка пришлась на
организацию без сайта.

По стратам потери распределены неравномерно. ИП и малые компании закрыты почти
полностью: там правильный ответ это null. Пропуски сосредоточены в крупном
бизнесе, и причины понятны: ozon.ru отвечает 403, wildberries.ru не публикует
ИНН на главной, у «АЭМ-технологий» и БГТУ им. Шухова домен не выводится из
названия. В каждом таком случае LLM называла верный домен, но независимой опоры
не находилось, и пайплайн выбирал молчание.

Полный разбор ошибок и план улучшений лежат в `eval/report.md`. Коротко: первым
делом рендеринг JavaScript на крупных доменах, затем сужение понятия опоры до
«домен назван в карточке организации», затем данные регистратора вместо
закрытого WHOIS.

Оговорка про статистику: 35 наблюдений дают широкий доверительный интервал, для
точности 0.93 при 15 ответах это примерно от 0.70 до 0.99. Выводы выше опираются
на разбор конкретных ошибок, а не на третий знак после запятой.

## Что я знаю про ограничения этого решения

- Крупные площадки закрыты от ботов: ozon.ru отвечает 403 на обычный запрос.
  Часть сайтов отдаёт пустой HTML и рисует содержимое на JavaScript, как
  yandex.ru. Реквизитов в таком ответе нет, и такие организации уходят в null.
  Лечится headless-браузером на избранных доменах.
- Разметка сделана вручную по доказательствам, набор небольшой, доверительные
  интервалы у метрик широкие. Для продакшена нужна стратифицированная выборка на
  тысячу с лишним записей и два независимых разметчика.
- Пайплайн отвечает по одному ИНН. Для массовой обработки нужны очередь,
  параллелизм и соблюдение лимитов провайдеров.
- Лицензии поисковых API ограничивают хранение выдачи, для коммерческого
  справочника условия нужно читать отдельно.
- Стоимость на один ИНН складывается из пяти поисковых запросов, до двадцати
  загрузок страниц и одного-двух вызовов LLM. Это допустимо для точечных
  запросов и неприемлемо для полного прохода по ЕГРЮЛ. Как строить справочник
  массово, описано в ответе на задание 1.
