# Задание 2. Пайплайн «ИНН → домен»

Код: https://github.com/zubarevdm/inn-to-domain

```
$ inn2domain 7721581040        $ inn2domain 7805590027
{"domain": "dadata.ru"}        {"domain": null}
```

Второй пример важнее первого. ООО «ПЛАСТ» из Петербурга сайта не имеет, при этом
домен plast.ru существует и принадлежит другой компании из Москвы. Вся
конструкция подчинена одной идее: неверный домен дороже пустого поля, потому что
пустое поле клиент увидит, а неверное примет за правду.

**Инструменты.** Стек российский, работает без VPN: GigaChat для анализа,
Yandex Search API для поиска (русский малый бизнес Яндекс индексирует полнее
зарубежных поисковиков), DaData для карточки организации. Поисковый провайдер
меняется одной переменной окружения, второй реализацией подключён Exa. Python,
httpx, pydantic, без LangChain: в задаче четыре шага и одна модель, прозрачность
важнее готовых абстракций. Поиск, страницы и вызовы LLM кэшируются в SQLite:
бесплатные лимиты конечны, а прогоны оценки должны воспроизводиться.

## Этапы

**1. Валидация ИНН** по контрольной сумме, чтобы мусор не доходил до платных API.

**2. Карточка организации из ЕГРЮЛ** через DaData. По одному ИНН поисковик
выдаёт агрегаторы реквизитов, самого сайта в выдаче нет, поэтому искать надо по
названию, бренду и городу, а проверять найденное по ИНН и ОГРН.

**3. Пять поисковых запросов.** Каждый слеп по-своему. Запрос по ИНН выводит
агрегаторы, зато их сниппеты часто содержат адрес сайта. Запрос по названию
юрлица бесполезен, когда бренд с ним не совпадает: ООО «Интернет Решения» это
ozon.ru, ООО «Дейта Кью» это dadata.ru. Запрос по названию с городом помогает
малому бизнесу с типовым именем.

**4. Сборка кандидатов.** Домены нормализуются: www убирается, punycode
раскрывается в юникод, поддомены схлопываются. Для конструкторов сайтов
исключение: `my-shop.tilda.ws` остаётся целиком, там поддомен и есть сайт.

Агрегаторы и маркетплейсы обычный блок-лист выбрасывает целиком, и это ошибка:
каждый портал сам является чьим-то сайтом, по ИНН 7704217370 правильный ответ
это ozon.ru. Правило мягче: портал проходит, если на его главной или в контактах
опубликованы реквизиты запрошенной организации либо домен совпадает с брендом.
Чужие ИНН площадки публикуют на глубоких страницах, куда пайплайн не заходит.

Второй источник кандидатов — домены, написанные словами в тексте выдачи («Сайт:
ozon.ru» в карточке агрегатора). Вернуть агрегатор как ответ нельзя, а взять его
подсказку и проверить самостоятельно можно.

**5. Проверка кандидатов.** Загружаются главная, найденные в разметке ссылки на
контакты и реквизиты, а также типовые адреса `/contacts`, `/about`, `/rekvizity`
напрямую: у сайтов на JavaScript ссылок в HTML нет. В тексте ищутся ИНН и ОГРН,
цифры могут быть разделены пробелами. Отдельно отслеживается ловушка: ИНН
веб-студии в подвале («разработка сайта, ООО ...») доказательством не считается.

Дополнительно опрашивается WHOIS. Реестр .ru отдаёт поля `org` и `taxpayer-id`,
то есть название и ИНН владельца домена, и это была бы прямая официальная
связка, но проверка на живых доменах показала, что оба поля скрыты. Остаётся
дата регистрации, нужная для контроля перехвата освободившихся доменов.

Ещё одна находка: крупные российские сайты (sberbank.ru, vtb.ru, gazprom.ru)
выпускают сертификаты в НУЦ Минцифры, которого нет в бандле certifi. Без
повторной загрузки в обход проверки цепочки они считаются мёртвыми.

**6. Решение LLM.** GigaChat получает карточку и кандидатов с доказательствами,
возвращает строгий JSON. Два правила снимают известные риски: модель выбирает
домен из списка кандидатов, ответ вне списка отбрасывается кодом, а содержимое
страниц подаётся отдельным блоком с пометкой «недоверенные данные», потому что
на сайте может лежать текст, адресованный модели. Если уверенности нет, модель
возвращает дополнительный поисковый запрос, и пайплайн делает второй круг.

**7. Политика ответа.** Решение принимает код. Реквизиты организации на сайте
дают ответ с уверенностью 0.9–0.97. Если модель называет другой домен, арбитром
выступает она (почему — ниже), но её выбор обязан иметь независимую опору: домен
назван в карточке организации, совпадает с корпоративной почтой либо совпадает с
брендом вместе с городом на странице. Одного совпадения названия мало. Во всех
остальных случаях ответ null.

## Оценка качества

Набор из 35 организаций: крупный бизнес, средние компании, вузы, малые ООО с
типовыми названиями и шесть ИП. У 23 сайт есть, у 12 нет. Метки ставились
вручную по выдаче и реквизитам, ответы пайплайна в разметке не участвовали.

| метрика | только поиск | поиск + проверка реквизитов | полный пайплайн |
|---|---|---|---|
| выдано доменов | 34 | 4 | 15 |
| точность | 0.38 | 0.0 | **0.93** |
| полнота | 0.57 | 0.0 | 0.61 |
| верных null | 0.0 | 1.0 | 0.92 |
| неверных доменов | 9 | 4 | **0** |
| ложных ответов там, где сайта нет | 12 | 0 | 1 |

Базовый режим «первый неагрегатор из выдачи» ошибается в двух случаях из трёх и
не умеет молчать: на 12 организациях без сайта он выдал 12 доменов.

Проверка реквизитов без LLM даёт обратную крайность: отвечает 4 раза из 35 и все
четыре раза ошибается. ИНН «Ростелекома» нашёлся на checko.ru, ИНН «Альфа-Банка»
на alfabank.cards, ИНН вуза на сайте филиала. Отсюда правило, которое я заложил
в политику после прогона: реквизиты доказывают, что организация упомянута, но не
то, что сайт принадлежит ей, поэтому при расхождении решает модель.

Полный пайплайн отвечает 15 раз и ошибается один раз, ни разу не назвав чужой
домен организации, у которой сайт есть. ИП и малые компании закрыты полностью:
там верный ответ это null. Пропуски сосредоточены в крупном бизнесе: ozon.ru
отвечает 403, wildberries.ru не публикует ИНН на главной, у «АЭМ-технологий» и
БГТУ им. Шухова домен не выводится из названия. В каждом таком случае модель
называла верный домен, но опоры не находилось, и пайплайн выбирал молчание.

35 наблюдений дают широкий доверительный интервал: для точности 0.93 при 15
ответах это примерно от 0.70 до 0.99. Выводы опираются на разбор конкретных
ошибок, он лежит в `eval/report.md`.

## Ограничения и что делать дальше

- Рендеринг JavaScript на крупных доменах: главная причина пропусков.
- Сузить понятие опоры до «домен назван в карточке организации»: убирает
  единственный ложный ответ.
- Данные регистратора вместо закрытого WHOIS превратили бы половину задачи в
  обычный джоин.
- Стоимость одного ИНН: пять поисковых запросов, до двадцати загрузок страниц и
  один-два вызова LLM. Для точечных запросов приемлемо, для полного прохода по
  ЕГРЮЛ нет; как строить справочник массово, описано в задании 1.
- Лицензии поисковых API ограничивают хранение выдачи, для коммерческого
  справочника условия нужно читать отдельно.
